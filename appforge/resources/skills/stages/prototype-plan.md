# Prototype-plan director

State the hypothesis the prototype must test and the smallest runnable slice that can test it. A prototype is not permission to be vague; it is permission to make deliberate, documented shortcuts.

List what must be demonstrated, the timebox, sample data, success signals, and which production concerns are intentionally deferred. Choose shortcuts that are reversible and do not create security hazards. Do not fake the core behavior being evaluated.

Prefer one vertical path through the product over many incomplete screens. Reuse stable libraries and local services. Avoid distributed infrastructure, premature abstraction, and broad compatibility work unless they are the hypothesis.

Define what happens after the demo: discard, iterate, or harden. Make the gap between prototype and production explicit so the handoff does not overstate readiness.
