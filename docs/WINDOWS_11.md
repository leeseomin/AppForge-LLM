# Windows 11 support and security model

This build keeps the existing one-click Windows launcher and adds a native execution boundary for projects generated by AppForge. The web application itself runs as the signed-in user; commands requested by generated projects run in a separate per-workspace AppContainer and Job Object.

## Supported path

Use a current 64-bit Windows 11 installation with:

- an NTFS project drive;
- Windows PowerShell 5.1 or PowerShell 7;
- Python 3.11 or newer;
- Node.js 22 and npm;
- the Bun version recorded in `.bun-version`.

The AppContainer implementation does **not** require the optional Windows Sandbox feature or Hyper-V. A FAT/exFAT drive or a network share that cannot apply Windows ACLs is rejected rather than falling back to unrestricted execution.

## First run

From File Explorer, double-click `build.bat`. From Command Prompt or PowerShell:

```bat
build.bat
```

Before a normal launch, run the full Windows preflight once:

```bat
build.bat --check
```

`--check` installs or verifies dependencies, builds the packaged web assets, and launches a harmless Python command through the same AppContainer and Job Object path used for generated projects. A failure is reported as `EXECUTION_SANDBOX_UNAVAILABLE`; AppForge does not silently execute the project on the host.

A bounded web smoke check is also available:

```bat
build.bat --smoke --no-open
```

## Generated-command isolation

Each generated workspace receives a stable profile name derived from the normalized workspace path. The corresponding AppContainer SID is granted:

- **Modify** access to that workspace and its disposable sandbox home;
- **Read/execute** access only to approved Python, Node.js, Bun, Git, Java, .NET, and package-manager toolchain roots;
- no general access to the signed-in user's profile, browser data, credential stores, clipboard, or other project workspaces.

The process starts suspended, is assigned to a Job Object, and is then resumed. The Job Object applies:

- kill-on-close process-tree cleanup;
- a process-count limit;
- a total memory limit;
- a CPU-rate hard cap;
- UI and clipboard restrictions.

Defaults are 4,096 MiB, 64 processes, and an 80% CPU rate. Trusted host configuration may change them before AppForge starts:

```powershell
$env:APPFORGE_WINDOWS_SANDBOX_MEMORY_MB = "8192"      # 256..32768
$env:APPFORGE_WINDOWS_SANDBOX_MAX_PROCESSES = "96"    # 1..512
$env:APPFORGE_WINDOWS_SANDBOX_CPU_RATE = "9000"       # 100..10000; 10000 = 100%
```

The normal command timeout remains the outer wall-clock limit. If the trusted helper times out or terminates, closing its Job Object terminates descendants as well.

## Network policy

Generated commands receive no AppContainer network capability by default. Dependency installation or another explicitly network-approved tool invocation adds only the Windows `internetClient` capability for that process. No private-network capability or loopback exemption is added.

Network permission and dependency-install permission remain separate policy decisions:

- `allow_network`: permits a network-capable command selected by policy;
- `allow_dependency_install`: permits dependency resolution into the generated workspace;
- neither setting permits a raw shell or a destructive command by itself.

## Windows command policy

Policy checks canonicalize Windows executable aliases before classification. For example, `cmd`, `cmd.exe`, `C:\Windows\System32\cmd.exe`, `npm.cmd`, and `git.exe` cannot bypass the same shell, network, or dependency rules through a suffix or path spelling.

Explicit `cmd.exe`, `powershell.exe`, and `pwsh.exe` execution requires destructive opt-in. Direct Windows deletion or disk-management aliases such as `del`, `erase`, `rd`, `rmdir`, `diskpart`, and `format` are denied by default.

Package-manager batch launchers such as `npm.cmd` and `gradlew.bat` are not exposed as an arbitrary shell. After policy validation, the trusted helper invokes them through a fixed, non-interactive PowerShell argument-forwarding script inside the AppContainer.

## API-key storage

On Windows, `APPFORGE_LLM_SECRET_BACKEND` defaults to `dpapi`.

- API keys are encrypted with Windows DPAPI `CurrentUser` scope.
- `providers.json` stores only a reference such as `dpapi:appforge-llm/openai/apiKey`.
- encrypted blobs are stored separately in `secrets.dpapi.json`.
- plaintext legacy entries are migrated on the next successful load/save.
- secret material is sent to the fixed PowerShell DPAPI bridge through standard input, never as a process argument.

The macOS default remains Keychain, and Linux retains the private-file backend. A backend may be selected explicitly for migration or testing:

```powershell
$env:APPFORGE_LLM_SECRET_BACKEND = "dpapi"  # Windows recommended
```

DPAPI protects against another Windows account or an offline copy of the file. Malware already running as the same signed-in user can still ask Windows to decrypt CurrentUser data, so normal endpoint security remains necessary.

## Continuous verification

`.github/workflows/windows-ci.yml` runs on GitHub's hosted `windows-2025` image and covers:

- the PowerShell and batch launchers;
- AppContainer filesystem and loopback denial tests;
- Job Object descendant cleanup;
- Python tests;
- frontend tests and production build;
- Bun bridge typecheck and tests, including a real DPAPI round trip;
- the web health/UI smoke path.

Hosted Windows CI is not identical to a consumer Windows 11 desktop. `.github/workflows/windows11-release-smoke.yml` is a manual gate for a self-hosted runner labeled `appforge-win11` on real Windows 11 hardware.

## Troubleshooting

### `EXECUTION_SANDBOX_UNAVAILABLE`

Run:

```bat
build.bat --check
```

Then verify:

1. the source and generated-project directories are on NTFS;
2. `icacls.exe` and Windows PowerShell are available under `%SystemRoot%\System32`;
3. endpoint policy has not disabled AppContainer profile creation or child-process assignment to Job Objects;
4. Python, Node.js/npm, Bun, and Git are installed in normal toolchain directories;
5. the workspace path is not an ACL-incompatible network mapping.

No unrestricted fallback is provided. Move the project to a local NTFS folder or adjust the enterprise policy, then repeat `--check`.

### A build exceeds a resource limit

Raise only the needed trusted-host setting shown above, restart AppForge, and rerun the stage. Do not pass these settings through generated project tool arguments.

### Dependency installation cannot reach a registry

Confirm the project safety settings permit dependency installation. The default no-network sandbox is intentional; changing firewall rules alone does not add the AppContainer capability.

### API key cannot be decrypted

DPAPI ciphertext is bound to the Windows user profile. Re-enter the provider key after changing Windows accounts, restoring only part of a profile, or moving the configuration from another machine.
